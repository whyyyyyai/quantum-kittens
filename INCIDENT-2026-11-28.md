Written by: vibe (2026-11-28)

## Timeline

- **10:06:36–10:06:42** — the session is still alive; the deck wakes vibe
  (1 note) and claude (1 note).
- **10:06:45** — the kernel **global OOM killer** fires on an order-3
  allocation (`ffmpeg invoked oom-killer ... global_oom`). It kills
  **kitty pid 440960** (`kitty-1052-0.scope`, `oom_score_adj=1000`) and
  **grok-bot pid 806458** (1.5 GiB total-vm, `oom_score_adj=300`, inside
  the `wayland-wm@hyprland.desktop.service` cgroup). systemd logs OOM
  kills in `kitty-1052-0.scope`, `app.slice`, `session.slice` and
  `wayland-wm@hyprland.desktop.service`. Memory at the time: 7.2 GiB RAM
  with ~33 MiB free and 692 MiB of the 39 GiB swap in use — swap exists
  now, but reclaim could not satisfy the allocation.
- **10:06:45** — session teardown begins: warp-core stops **cleanly**
  ("warp-core: stopping; GPU drained: true"; the old instance, pid
  1031563, had 837 MiB peak memory over its 30 min life), webcam-feed,
  portals, mako, blueman, hypr-recover and scratchpad-keeper all stop.
- **10:06:46** — `wayland-wm@hyprland.desktop.service` fails with result
  **`oom-kill`**; uwsm tears the session down.
- **10:06:47** — sddm logs the session close and a fresh login (PAM
  audit records).
- **10:06:52** — uwsm starts a new Hyprland (pid 1072642) and
  `quantum-kittens-launch.service` runs `launch-desktop` on
  `~/.config/quantum-kittens/launch.conf`. warp-core restarts (pid
  1072812) after `gpu-ok.sh` passes; webcam-feed comes back
  (`/dev/video1 640x480 @8fps`). Every window reopens: comms-deck chat
  full and half, mail, and the grok, claude and vibe terminals.
- **10:06:53+** — warp-core is healthy: Apple M1 (Vulkan/Honeykrisp,
  Mesa 26.3.1), 779 entities, 26.4 fps, worst frame 329 ms while hidden.
  By 10:09: 781 entities. The deck was serving notes again throughout.

## What survived and what died

**Survived untouched** (user services, not desktop clients):

- `comms-deck serve` (pid 322258, up since 27 Nov 01:16), push-courier,
  scratchpad-keeper, `warp-core-prices` (price feed, up since 04:17) —
  the deck never went down and queued nothing late.

**Killed at 10:06:45**: one kitty window (pid 1052's scope — 1h38m CPU
over 7h, 100 MiB peak), grok-bot (504 MiB peak, 335 MiB swap), and
Hyprland itself, which is what turned a memory spike into a full
session restart.

**Came back by 10:06:52**: the compositor, every agent window, warp-core,
the webcam feed. Nothing was lost; no notes were dropped.

## Cause

Memory pressure on an 8 GiB machine where the GPU shares system RAM:
several kitty windows plus five agent CLIs plus warp-core on the GPU plus
grok-bot, with only ~33 MiB free. The kernel's lever was killing
processes, and it picked a kitty and grok-bot — and the hit landed in
Hyprland's cgroup, so the compositor died and took the session with it.
Unlike the 26 Nov 02:11 incident there was swap this time (39 GiB), but a
global order-3 allocation still triggered the OOM killer.

Related, but **not** this crash: `~/.local/state/warp-core/crash.log`
shows warp-core's own code panics — 6× wgpu-hal "Requested feature is
not available on this device" (27 Nov 05:30, the documented GPU fault
window) and bevy_ecs `B0001` conflicting-query panics (27 Nov 06:08 ×3,
28 Nov 07:46 ×1). The 07:46 panic killed the warp-core instance of that
morning; the 10:06 event was a clean stop during the session teardown.

## Recommendations, in order of leverage

1. **Protect the compositor and the deck from the OOM killer** — a
   negative `oom_score_adj` on Hyprland and `comms-deck` would have kept
   the session up through this spike. This is the difference between a
   killed terminal and a whole-desktop restart.
2. **Close stale kitty windows, and restart agent terminals that pass
   ~1 GiB** — the killed kitty had lived 7 h.
3. **Fix the warp-core code panics** recorded in `crash.log`: the bevy
   `B0001` query conflict (last seen 07:46 today — needs
   `Without<T>`/`ParamSet`) and the wgpu-hal feature request that is not
   available on the M1.
4. Keep what already worked: `gpu-ok.sh` + `Restart=always` +
   `StartLimitBurst=3` brought warp-core back in 7 s, and
   `launch-desktop` reopened every window without duplicating anything.

## What went right

The same machinery as the 26 Nov incident, working as designed: the
deck services live outside the desktop's slices and never noticed; the
note queue is on disk; `launch-desktop` is idempotent; warp-core's GPU
guard and restart policy absorbed the stop cleanly ("GPU drained:
true"). Total visible outage: about seven seconds, 10:06:45–10:06:52.
